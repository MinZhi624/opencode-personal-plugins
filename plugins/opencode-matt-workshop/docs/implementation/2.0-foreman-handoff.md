- Generate one normalized manifest from upstream metadata plus local OpenCode policy. Commands, permissions, synchronization checks, and registration checks consume it.
- Register a same-name Workflow Command for every Promoted Skill.

## Guarded Workflow Commands

These commands set `agent` and therefore persistently switch the current OpenCode session before execution:

- Foreman: `implement`, `tdd`, `diagnosing-bugs`, `prototype`, `resolving-merge-conflicts`, `wizard`
- Drafter: `triage`, `to-spec`, `to-tickets`, `wayfinder`

The other 15 commands omit `agent` and run in the current Primary Agent. If its Skill whitelist denies the requested Skill, report the required manual Agent switch rather than widening permissions or silently routing it.

## Core release acceptance contract

All five groups are blocking and must run in GitHub Actions without downloading upstream content:

1. **Upstream consistency**
   - Vendored metadata identifies `v1.2.2` and the fixed commit.
   - The promoted manifest contains exactly 25 Skills.
2. **Reproducible synchronization**
   - Regeneration from the vendored snapshot produces byte-identical committed adapted output.
   - Overlay anchor mismatch fails closed.
3. **Registration consistency**
   - Exactly 25 adapted Skills and 25 same-name commands.
   - Exactly 14 user-only and 11 model-invocable Skills.
   - Exactly the 10 guarded bindings above.
   - Agent whitelist references resolve; `to-issues` and `writing-great-skills` do not exist at runtime.
   - `/to-tickets` loads `to-tickets` directly.
4. **Build consistency**
   - TypeScript typecheck/build passes.
   - Committed `dist` equals a clean rebuild from `src`.
5. **Distribution isolation**
   - A staging allowlist constructs the installable bundle.
   - The staged bundle excludes vendor, CONTEXT files, ADRs, AI instructions, TypeScript source, tests, and development-only synchronization tools.
   - It includes runtime `dist`, all 25 adapted Skills and their required resources, user documentation, licenses, and third-party notices.

Full cross-platform installation smoke tests are desirable follow-up work, but are not part of the five blocking 2.0 gates. The blocking packaging and synchronization tools should still be platform-neutral Node programs where practical.
